# Тести на хості

Тести драйверів `firmware/Devices/` і прикладної логіки `firmware/App/` для звичайного ПК (ЛР2 §4.6). Плата для них не потрібна. Код прошивки компілюється без змін, а шар під ним (`Platform/` для драйверів, `Devices/` для `App`) замінюється підробками (test doubles) з `doubles/`.

## Запуск

З кореня репозиторію, у тому самому Docker-образі, що й `make build` (`docker/Dockerfile`):

```
make test        # зібрати й запустити всі тести
make coverage    # те саме з покриттям, звіт у tests/build/coverage/index.html
```

Після зміни `docker/Dockerfile` образ треба один раз перезібрати: `docker build -t stm32-build docker/`.

Параметри (передаються в `make -C tests`):

| Параметр | Що робить |
|---|---|
| `COVERAGE_MIN=<n>` | мінімальне покриття рядків у %, за замовчуванням 95 |

## Будова

```
tests/
├── Makefile
├── test_*.c              тести, по одному виконуваному файлу на драйвер або модуль App
├── doubles/              підробки шару Platform; заглушка шару Devices для тестів App
├── vectors/              тестові вектори з записів логічного аналізатора
├── tools/                генератор векторів з експорту PulseView
└── vendor/unity/         Unity v2.6.0, версія зафіксована у VERSION.md
```

Кожен тест драйвера збирається з драйвером, який перевіряє, і з тими підробками, через які цей драйвер звертається до шини. Тест модуля `App` збирається з цим модулем і заглушкою драйверів `stub_devices.c` замість справжнього шару `Devices`. Виклики `printf()` у коді прошивки при збірці тестів перенаправляються (`-Wl,--wrap=printf`) у буфер `doubles/uart_capture.c`. Так тест порівнює саме той текст, який прошивка друкує в UART.

### Fake і mock

| Підробка | Вид | Що робить |
|---|---|---|
| `fake_i2c` | fake | регістри для кожної I2C-адреси; відсутній пристрій відповідає NACK; помилку можна підставити на N-ту транзакцію або на конкретний регістр |
| `fake_w25q64` | fake | робоча модель флешки: 8 МБ пам'яті, біти BUSY і WEL, команди `06 04 05 9F AB 02 20 D8 03 0B`. Запис і стирання діють лише після Write Enable, як у справжньому чіпі. Можна імітувати відсутній чіп, вічний BUSY і WP# |
| `mock_spi` | mock | моделі чіпа немає зовсім: тест задає точний список кадрів CS#, і mock валить тест на першому зайвому, пропущеному чи неправильному байті |
| `fake_sccb` | fake | регістри OV7670; записує трафік у тому самому вигляді, що й вектор із запису |
| `fake_pwm`, `fake_time` | fake | налаштування таймера і ширина імпульсу; тік, що росте на 1 мс за кожне читання, щоб будь-який цикл з тайм-аутом завершувався |
| `stub_devices` | stub | замінює драйвери для тестів `App`: кожна функція лише записує свій виклик у лог і повертає заданий тестом результат (`stub_gy89_ok = false` — «GY-89 не відповів») |

**Fake** — це спрощена робоча реалізація: тест перевіряє *результат*, тобто дані, стан пам'яті й повернені коди. **Mock** перевіряє *поведінку*: що драйвер надіслав саме ці команди, саме в такому порядку і нічого понад це. Обидва потрібні для флешки. Тест з fake (`test_w25q64.c`) перевіряє, що після стирання блок читається як `FF`, а записані дані збігаються з прочитаними. Тест з mock (`test_w25q64_sequence.c`) перевіряє, що `06` (Write Enable) іде перед `D8` і що після відмови у WEL драйвер нічого більше не надсилає. Fake помітив би таку зайву команду лише опосередковано.

## Тестові вектори з записів

`vectors/` містить байти, які справді були на шині (`docs/captures/`, аналіз у `docs/captures/analysis.md`):

| Вектор | Звідки | Перевіряє |
|---|---|---|
| `capture_vectors.h`: температура | `i2c_init_temp_check.sr`, 1130–10775 мс: `F1 80`, `F1 A0`, `F1 90`, `F1 B0` | `MPU6050_ReadTemperature` дає 25,61 / 25,71 / 25,66 / 25,75 °C |
| `capture_vectors.h`: ID | той самий запис, 4978–4995 мс | `GY89_ReadIDs` приймає ці ID як правильні і друкує їх з `(OK)` |
| `ov7670_cif_init_vector.h` | `i2c_init_temp_check.sr`, 5330–5489 мс, 137 транзакцій SCCB | `ov7670_configure(1)` видає на шину ту саму послідовність, транзакція в транзакцію |

`ov7670_cif_init_vector.h` не пишеться вручну, а генерується з експорту PulseView:

```
python3 tests/tools/gen_sccb_vector.py docs/captures/i2c_init_temp_check_export.txt tests/vectors/ov7670_cif_init_vector.h
```

Обмеження: лог UART того самого запуску не зберігся. Тому тести порівнюють надрукований текст з форматом, який прошивка використовує в `printf`, а не з рядками справжнього логу. Коли з'явиться запис, зроблений разом із логом терміналу, значення з логу додаються в `capture_vectors.h`.

## Що покрито

| Вимога §4.6 | Тести |
|---|---|
| сирі дані → фізичні одиниці | `test_mpu6050.c`: формула, точка з datasheet (−521 LSB = 35 °C, MPU-6000 Product Specification Rev 3.1, с. 14), знак 16-бітного числа, вектори з запису; `test_servo.c`: кут → імпульс, період 20 мс, обмеження 180° |
| помилки шини: NACK, timeout, неочікуваний ID | NACK і відсутній чіп: `test_mpu6050.c`, `test_gy89.c`, `test_w25q64.c` (MISO `FF`); timeout: `test_w25q64.c` (BUSY не знімається після стирання); неочікуваний ID: MPU-6500 (0x70), Macronix (`C2 20 17`), BMP280 (0x58) |
| послідовність команд SPI-flash | `test_w25q64_sequence.c` (mock), `test_w25q64.c` (fake) |
| вектори з логічного аналізатора | див. таблицю вище |
| приклад розрахунку з datasheet | `test_temperature_reproduces_datasheet_offset_point` |
| прикладна логіка (`App/`) | `test_selftest.c`: порядок перевірок на старті, рядки `SELFTEST <пристрій> OK/FAIL` і підсумок, відключений GY-89 дає `FAIL` і `3/4` |

Для BMP180 у прошивці немає розрахунку температури й тиску, лише читання ID. Тому відтворювати приклад компенсації з його datasheet нема на чому. Якщо драйвер BMP180 з'явиться, тест має відтворити приклад розрахунку з його datasheet.

Без тестів свідомо лишено:
- `Platform/` і `Core/`: це звертання до HAL і регістрів STM32, на ПК вони не виконуються, і в тестах саме вони замінені підробками;
- цикли зчитування кадру камери (`platform_camera.c`): їхня коректність залежить від тактів процесора, тож перевірити її можна лише на платі;
- `App/Src/console.c` (UART-команди) і `App/Src/app.c` (головний цикл): майже кожна команда лише передає аргументи драйверу камери чи флешки і друкує відповідь, а головний цикл залежить від кнопки, світлодіода і часу. Їх перевіряє учасник з платою;
- `App/Src/stream.c` (CRC-32 і base64 для передачі кадрів): методичка тестів для нього не вимагає, а помилку в ньому одразу видно на комп'ютері, бо `scripts/cam.py` перевіряє CRC кожного шматка кадру;
- `Devices/Src/ov7670_capture.c`: тонка обгортка над `platform_camera` і `platform_sccb`, без власної логіки;
- термостат з гістерезисом (FR-02/03) і блокування (FR-06) ще не написані. Тести для них додаються разом з ними.

## Покриття

`make coverage` рахує покриття для `firmware/Devices/` і `firmware/App/` (gcov + lcov 1.15, версія зафіксована в `docker/Dockerfile`):

| Файл | Рядки | Гілки |
|---|---|---|
| `App/Src/selftest.c` | 100 % (24) | 100 % (4) |
| `gy89.c` | 100 % (17) | 100 % (4) |
| `i2c_scan.c` | 100 % (9) | 100 % (4) |
| `mpu6050.c` | 100 % (22) | 100 % (8) |
| `ov7670.c` | 100 % (54) | 92,9 % (28) |
| `servo.c` | 100 % (9) | 100 % (2) |
| `w25q64.c` | 97,4 % (117) | 64,6 % (82) |
| **Разом** | **98,8 % (252)** | **76,5 % (132)** |

lcov рахує лише ті файли, які компілюються хоча б в один тест. Тому файли зі списку «Без тестів свідомо лишено» (`console.c`, `app.c`, `stream.c`, `ov7670_capture.c`) у таблиці відсутні, а не мають 0 %.

Непокрите:
- `w25q64.c`: тести перевіряють те, що вимагає §4.6 (ідентифікація, послідовність команд, Write Enable перед стиранням і записом, тайм-аут, «записане = прочитане»). Захисні перевірки аргументів (запис через межу сторінки, нульова довжина, читання за кінцем пам'яті), очікування зайнятого чіпа перед командою і коди помилок `w25_self_test` свідомо не тестуються. Звідси 64,6 % гілок. Функція `w25_set_speed` (команда `FSPEED`) лише передає дільник у `Platform_SPI_SetSpeed`.
- `ov7670.c`: вихід із циклу регістрів без маркера кінця `FF FF`. Він неможливий, бо кожна таблиця режимів закінчується маркером, і це окремо перевіряє `test_mode_table_is_consistent`.

**Поріг: 95 % рядків** для `Devices/` і `App/`, `make coverage` завершується з помилкою нижче нього. Ось чому:
- код цих шарів не залежить від заліза, тож на ПК досяжний увесь, і зараз покрито 98,8 %;
- запас у 5 % лишено для захисних перевірок, як у списку вище;
- якщо до вже протестованого файлу додати код без тестів, покриття падає нижче порогу, і це видно в CI. Зовсім новий файл без жодного тесту поріг не помітить (див. вище), тому новий файл треба одразу додавати в `tests/Makefile`.

Покриття гілок не обмежується порогом, а лише виводиться: захисні перевірки флешки свідомо не тестуються (див. вище).

## Перевірка самих тестів

Методичка цього не вимагає, але щоб переконатися, що тести справді ловлять помилки, у копію драйверів і `App` по одній вносились навмисні помилки, і після кожної запускався `make test`. Ось що впіймали тести:

| Внесена помилка | Що впало |
|---|---|
| стирання без Write Enable | 6 тестів |
| запис сторінки без перевірки WEL | 2 |
| Fast Read без фіктивного байта | 2 |
| тайм-аут стирання 3000 → 30 мс | 1 |
| температура як беззнакове число | 3 |
| зсув температури 36,53 → 35 | 4 |
| пропущено запис `PWR_MGMT_1` | 2 |
| прибрано обмеження кута 180° | 1 |
| кут ділиться на 200 замість 180 | 4 |
| скан не доходить до 0x7F | 1 |
| BMP180 читається з регістра D1 | 4 |
| GY-89 знову ігнорує NACK | 1 |
| пауза після скидання камери 100 → 10 мс | 1 |
| HREF: зберігаються не ті біти | 2 |
| FREEZE скидає й FASTAEC | 2 |
| самоперевірка рахує FAIL як OK | 1 |

Усі 16 помилок впіймано.
