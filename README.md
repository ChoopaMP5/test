# Модульні тести на хості

Каталог містить модульні тести для коду прошивки з `firmware/Devices/` (драйвери пристроїв) і `firmware/App/` (прикладна логіка). Тести збираються звичайним `gcc` і запускаються на ПК, плата для них не потрібна. Запуск: `make test`, з покриттям — `make coverage` (з кореня репозиторію).

Код прошивки в тестах не змінюється. Замість справжньої шини (I2C, SPI, SCCB, PWM) драйвер отримує підробку з каталогу `doubles/`, яка поводиться як пристрій. Для тестів `App` так само підміняються драйвери.

## 1. Структура каталогу

```
tests/
├── Makefile
├── test_*.c          тести, по одному файлу на драйвер або модуль App
├── doubles/          підробки шин і драйверів
├── vectors/          дані, записані логічним аналізатором
├── tools/            скрипт, що робить вектор з експорту PulseView
└── vendor/unity/     фреймворк Unity v2.6.0 (версія записана у VERSION.md)
```

Кожен тест — окрема програма: драйвер + підробка його шини + сам тест.

Усе, що прошивка друкує через `printf()`, у тестах потрапляє не на екран, а в буфер (`doubles/uart_capture.c`). Тест читає цей буфер і перевіряє, що прошивка вивела б у UART саме потрібний текст.

## 2. Підробки

| Підробка | Вид | Що робить |
|---|---|---|
| `fake_i2c` | fake | зберігає регістри для кожної I2C-адреси. Якщо пристрою на адресі немає, відповідає NACK. Можна змусити помилитися на будь-якій транзакції |
| `fake_w25q64` | fake | спрощена флешка: 8 МБ пам'яті, біти BUSY і WEL, основні команди. Як і справжній чіп, пише і стирає лише після Write Enable. Може прикидатися відсутнім чіпом, вічно зайнятим чіпом або чіпом із захистом від запису |
| `mock_spi` | mock | не моделює чіп. Тест заздалегідь каже, які байти мають піти по SPI, і mock одразу валить тест, якщо драйвер надіслав щось інше |
| `fake_sccb` | fake | регістри камери OV7670. Записує все, що драйвер надіслав, щоб порівняти із записом з аналізатора |
| `fake_pwm`, `fake_time` | fake | таймер для сервоприводу; годинник, який при кожному зверненні йде на 1 мс вперед, щоб очікування з тайм-аутом не висіли |
| `stub_devices` | stub | замість драйверів для тестів `App`. Повертає те, що задав тест: наприклад, `stub_gy89_ok = false` означає «GY-89 не відповів» |

Різниця між fake і mock:
- **fake** — робоча, але спрощена модель пристрою. Тест дивиться на *результат*: що прочиталося, що лежить у пам'яті, що повернула функція;
- **mock** перевіряє *порядок дій*: які саме байти драйвер надіслав і в якій послідовності.

Для флешки є обидва. `test_w25q64.c` (fake) перевіряє, що після стирання пам'ять читається як `FF`, а записане читається назад без змін. `test_w25q64_sequence.c` (mock) перевіряє, що Write Enable (`06`) іде перед стиранням (`D8`), і що драйвер зупиняється, якщо чіп не дозволив запис.

## 3. Дані з логічного аналізатора

У `vectors/` лежать байти, які справді пройшли по шині на платі. Записи — у `docs/captures/`, розбір — у `docs/captures/analysis.md`.

| Файл | Звідки | Що перевіряє |
|---|---|---|
| `capture_vectors.h`: температура | `i2c_init_temp_check.sr`, 1130–10775 мс: `F1 80`, `F1 A0`, `F1 90`, `F1 B0` | `MPU6050_ReadTemperature` перетворює ці байти в 25,61 / 25,71 / 25,66 / 25,75 °C |
| `capture_vectors.h`: ID чіпів | той самий запис, 4978–4995 мс | `GY89_ReadIDs` визнає ці ID правильними і друкує `(OK)` |
| `ov7670_cif_init_vector.h` | `i2c_init_temp_check.sr`, 5330–5489 мс, 137 записів у камеру | `ov7670_configure(1)` надсилає камері ті самі 137 записів у тому самому порядку |

`ov7670_cif_init_vector.h` не набирається вручну, його створює скрипт:

```
python3 tests/tools/gen_sccb_vector.py docs/captures/i2c_init_temp_check_export.txt tests/vectors/ov7670_cif_init_vector.h
```

## 4. Що перевіряють тести

| Що | Де |
|---|---|
| перерахунок сирих даних у фізичні величини | `test_mpu6050.c`: формула температури, приклад з datasheet (−521 LSB = 35 °C, MPU-6000 Product Specification Rev 3.1, с. 14), від'ємні значення, дані з аналізатора; `test_servo.c`: кут → тривалість імпульсу, період 20 мс, кут не більше 180° |
| пристрій не відповідає (NACK) | `test_mpu6050.c`, `test_gy89.c`, `test_w25q64.c` (по SPI відсутній чіп дає `FF`) |
| пристрій завис (тайм-аут) | `test_w25q64.c`: флешка не закінчує стирання |
| на шині не той чіп | MPU-6500 (ID 0x70) замість MPU-6050, Macronix (`C2 20 17`) замість W25Q64, BMP280 (0x58) замість BMP180 |
| порядок команд флешки | `test_w25q64_sequence.c` (mock), `test_w25q64.c` (fake) |
| самоперевірка під час запуску (`App`) | `test_selftest.c`: пристрої перевіряються в правильному порядку, друкуються рядки `SELFTEST <пристрій> OK/FAIL` і підсумок; якщо GY-89 не відповів, буде `FAIL` і `3/4` |

## 5. Покриття

Покриття показує, яка частина коду хоча б раз виконалась під час тестів. Рахується для `firmware/Devices/` і `firmware/App/`. Звіт у браузері: `tests/build/coverage/index.html`.

| Файл | Рядки | Гілки |
|---|---|---|
| `App/Src/selftest.c` | 100 % (24) | 100 % (4) |
| `gy89.c` | 100 % (17) | 100 % (4) |
| `i2c_scan.c` | 100 % (9) | 100 % (4) |
| `mpu6050.c` | 100 % (22) | 100 % (8) |
| `ov7670.c` | 100 % (54) | 92,9 % (28) |
| `servo.c` | 100 % (9) | 100 % (2) |
| `w25q64.c` | 97,4 % (117) | 64,6 % (82) |
| **Разом** | **98,8 % (252)** | **76,5 % (132)** |

**Рядки** — скільки рядків коду виконалось. **Гілки** — скільки варіантів кожного `if` спрацювало. У кожного `if` є два варіанти (умова виконалась і не виконалась), і щоб гілки були покриті повністю, тести мають пройти обидва.

lcov рахує лише файли, які входять хоча б в один тест. Модулі, що працюють безпосередньо із залізом (`Platform/`, `Core/`, зчитування кадру, головний цикл і команди UART), перевіряються на платі, тому в таблиці їх немає.

### Чому покрито не все

**Рядки.** Не виконується лише функція `w25_set_speed`. Вона в один рядок передає дільник частоти SPI далі і нічого сама не рахує, тому тест для неї нічого б не перевірив.

**Гілки `w25q64.c`.** Непокриті гілки — це випадки, які або не трапляються на реальній шині, або нічого нового не перевіряють:
- **частини складених умов.** У перевірці на кшталт «усі три байти ID дорівнюють `FF`» lcov рахує кожне порівняння окремо. Тести перевіряють реальні відповіді (чіпа немає, правильний ID, чужий ID), а змішані відповіді на кшталт `FF FF 17` з шини не приходять;
- **пошкоджені дані.** Самоперевірка флешки порівнює записане з прочитаним, але підробка завжди зберігає дані правильно, тож гілка «не збіглося» не виконується. На платі така помилка видна одразу: команда `FTEST` друкує `[FAILED]` і номер першого неправильного байта;
- **неправильні аргументи**: нульова довжина, запис через межу сторінки, читання за кінцем пам'яті. Прошивка сама таких аргументів не створює, вони можливі лише при ручному введенні неправильної адреси в команді UART. Кожна така перевірка — одне порівняння;
- **повтори вже перевіреного.** Очікування, доки чіп звільниться, в усіх місцях робить одна функція, і її тайм-аут уже перевірено. Так само самоперевірка лише передає далі коди помилок функцій стирання, читання і запису;
- **перевірки на `NULL`.** Деякі функції дозволено викликати без вихідних параметрів, але прошивка завжди їх передає.

**Гілки `ov7670.c`.** Не покрито випадок, коли таблиця регістрів камери не закінчується маркером `FF FF`. У коді таких таблиць немає, і окремий тест `test_mode_table_is_consistent` це перевіряє.

### Пороги

**Рядки: мінімум 95 %.** Якщо менше, `make coverage` завершується з помилкою. Чому саме 95:
- код `Devices` і `App` не працює з залізом напряму, тому на ПК можна виконати майже весь. Зараз покрито 98,8 %;
- 100 % вимагати немає сенсу: тоді довелося б писати тести для однорядкових функцій на кшталт `w25_set_speed`, які нічого не перевіряють;
- 5 % запасу вистачає на такі рядки, а якщо хтось допише в драйвер помітний шматок коду без тестів, покриття впаде нижче 95 % і збірка покаже помилку.

Новий файл треба одразу додати в `tests/Makefile`: файл без жодного тесту в підрахунок не потрапляє, і поріг його не помітить.

**Гілки: порогу немає**, число лише виводиться. Майже всі непокриті гілки належать до випадків, описаних вище. Поріг на гілки змусив би писати тести саме на них, а нових помилок у роботі з пристроями такі тести не знайшли б. Важливі гілки (NACK, тайм-аут, чужий ID, відмова у дозволі запису) перевірено (розділи 2 і 4).

## 6. Помилки, знайдені тестами

Тести знайшли три місця, де драйвери не обробляли помилку шини. Усі три виправлено 22.10.2026, а тести залишено, щоб помилки не повернулися.

| № | Де | Що було | Тест | Що зроблено |
|---|---|---|---|---|
| DEFECT-1 | `mpu6050.c`, `MPU6050_Init` | якщо датчик не прийняв команду пробудження (NACK), він лишався в режимі сну, а в UART все одно писалося, що він прокинувся | `test_init_failed_wake_write_is_reported` | драйвер перевіряє результат запису, друкує помилку і повертає `false` |
| DEFECT-2 | `gy89.c`, `GY89_ReadIDs` | якщо чіп не відповів, друкувався ID попереднього чіпа | `test_nack_is_not_reported_as_a_valid_id` | друкується «Помилка зчитування по I2C!» |
| DEFECT-3 | `gy89.c`, `GY89_ReadIDs` | прочитані ID не порівнювалися з правильними (0x49, 0xD4, 0x55), тож чужий чіп проходив непоміченим | `test_unexpected_id_is_flagged` | ID порівнюються, функція повертає `true`/`false`, результат іде в самоперевірку (`SELFTEST GY89 OK/FAIL`) |
